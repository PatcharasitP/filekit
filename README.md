# FileKit — เครื่องมือจัดการไฟล์ที่ทำงานในเบราว์เซอร์ล้วน

🔗 **ใช้งานจริง: https://patcharasitp.github.io/filekit/** (ติดตั้งลงมือถือเป็นแอปได้ · ใช้ได้แม้ออฟไลน์)

เว็บแปลง/จัดการไฟล์ PDF · Excel · Word · PowerPoint · รูปภาพ **19 เครื่องมือ** ที่ประมวลผลในเครื่องผู้ใช้ทั้งหมด
ไม่มีการอัปโหลดไฟล์ขึ้นเซิร์ฟเวอร์ และใช้งานได้แม้ไม่มีอินเทอร์เน็ต

## ผลด้าน performance (วัดจริง ไม่ใช่ประมาณ)

เทียบกับเว็บต้นแบบ (`bbellechy.github.io/ILoveMyJob`) ที่โหลดไลบรารีทั้ง 9 ตัวแบบ blocking ตั้งแต่หน้าแรก
วัดด้วย Playwright + Chrome DevTools Protocol เงื่อนไขเดียวกันทั้งคู่ (เสิร์ฟจาก localhost, ไลบรารีชุดเดียวกัน):

**วัดบน production จริง — ทั้งสองเว็บอยู่บน GitHub Pages เหมือนกัน เน็ตจริงเงื่อนไขเดียวกัน:**

| ตัวชี้วัด | ต้นแบบ | FileKit | ผล |
|---|---:|---:|---|
| FCP — มือถือ Slow-4G + CPU ช้า 4× | 5,152 ms | **328 ms** | เร็วขึ้น **15.7×** |
| FCP — เดสก์ท็อป | 1,000 ms | **448 ms** | เร็วขึ้น 2.2× |
| ข้อมูลที่ต้องโหลดก่อนเห็นหน้าแรก | 831 KB | **13 KB** (29 KB ก่อนบีบ) | ลด **98%** |
| JavaScript ที่เบราว์เซอร์ต้อง parse | 3,603 KB | **27 KB** | ลด 99% |
| จำนวนไฟล์ที่ขอ | 12 | **5** | |
| หน่วยความจำหน้าแรก | 17 MB | **10 MB** | ลด 41% |

เทียบแบบตัดตัวแปรเครือข่ายออก (ทั้งคู่เสิร์ฟจาก localhost ไม่มี gzip ไลบรารีชุดเดียวกัน)
จะเห็นผลของสถาปัตยกรรมล้วน ๆ: FCP มือถือ 18,736 ms → 272 ms = **เร็วขึ้น 68.9×**

## ทำไมถึงเร็วกว่า — 7 อย่างที่ทำต่างออกไป

1. **หน้าแรกไม่โหลดไลบรารีสักตัว** — `src/registry.js` เก็บแค่ข้อมูลเครื่องมือ ไม่ import โค้ด
   ไลบรารีถูกดึงตอนเปิดเครื่องมือนั้นจริงผ่าน `src/loader.js` (แคช promise กันโหลดซ้ำ)
2. **Prefetch ตามเจตนา** — ชี้เมาส์/โฟกัสที่การ์ด = เริ่มดึงโค้ดเครื่องมือ + ไลบรารีทันทีใน `requestIdleCallback`
   ผู้ใช้ใช้เวลาจากชี้ถึงคลิกราว 100–300 ms ซึ่งพอให้โหลดล่วงหน้าได้
3. **Self-host ไลบรารีทั้งหมด** — ตั้งแต่ Chrome 86 แคชถูกแบ่งตามเว็บที่เรียก ไฟล์จาก CDN สาธารณะ
   จึงไม่ถูกใช้ซ้ำข้ามเว็บอีกแล้ว การ self-host ตัด DNS + TLS + connect ของโดเมนที่สามทิ้ง
   (`vendor/` มี fallback ไป CDN อัตโนมัติถ้าไฟล์หาย)
4. **CSS วิกฤตฝังใน HTML** — หน้าแรกวาดได้ครบโดยไม่รอไฟล์ CSS ภายนอก ส่วนสไตล์หน้าเครื่องมือโหลดทีหลัง
5. **ฟอนต์ไทย subset** — Sarabun ตัดเหลือเฉพาะช่วงอักขระที่ใช้: 90 KB → 45.7 KB ต่อน้ำหนัก และโหลดเมื่อจะสร้าง PDF เท่านั้น
6. **คืนคิวให้เบราว์เซอร์ระหว่างงานหนัก** — ทุกลูปประมวลผลเรียก `scheduler.yield()` (fallback `setTimeout`)
   จอจึงไม่ค้างและ INP ไม่พุ่งแม้กำลังแปลงไฟล์ใหญ่
7. **Service Worker** — GitHub Pages ตั้ง `max-age=600` เท่ากันหมดและไม่ส่ง brotli เราจึงคุมแคชเอง:
   `vendor/*` แบบ cache-first, ที่เหลือ stale-while-revalidate → เปิดซ้ำเร็วและใช้งานออฟไลน์ได้

## การใช้งานออฟไลน์ทำงานอย่างไร (และข้อจำกัดที่วัดมาแล้ว)

เว็บนี้ไม่ได้คุยกับเซิร์ฟเวอร์ระหว่างแปลงไฟล์อยู่แล้ว — โค้ดทั้งหมดรันในเบราว์เซอร์
Service Worker จึงทำได้แค่เก็บ "ตัวเว็บ" ไว้ในเครื่อง แล้วหลังจากนั้นทุกอย่างทำงานได้เองโดยไม่ต้องมีเน็ต

**แต่เดิมมีข้อจำกัดที่ต้องพูดตรง ๆ** (พิสูจน์ด้วยการตัดเน็ตระดับเครือข่ายจริง ไม่ใช่แค่ `navigator.onLine`):

| สถานการณ์ | ผลจริงที่วัดได้ |
|---|---|
| เครื่องมือที่เคยเปิดตอนมีเน็ตแล้ว | ✅ ใช้ออฟไลน์ได้ |
| เครื่องมือที่ยังไม่เคยเปิดเลย | ❌ ใช้ไม่ได้ (ไลบรารียังไม่ถูกเก็บ) |

เพราะไลบรารีถูกดาวน์โหลดแบบ on-demand ตามหลัก performance ข้างบน — ตอนเปิดหน้าแรกจึงมีไลบรารีเก็บไว้ **0 ไฟล์**

**วิธีแก้ที่เลือกใช้:** ปุ่ม **"เตรียมใช้งานออฟไลน์"** ท้ายหน้าแรก (`src/offline.js`)
กดครั้งเดียวจะดึงไลบรารี ฟอนต์ และโค้ดของทุกเครื่องมือ (~5 MB, 45 ไฟล์) มาเก็บไว้ล่วงหน้า
เลือกทำแบบให้ผู้ใช้กดเอง ไม่ใช่โหลดอัตโนมัติ เพราะการโหลด 5 MB ตั้งแต่หน้าแรกจะทำลายข้อดีเรื่องความเร็วทั้งหมด

หลังกดปุ่มแล้ว ทดสอบด้วยการตัดเน็ตจริง + เปิดเบราว์เซอร์ใหม่: Excel→PDF, PowerPoint→Word, PDF→Word และย่อรูป
**ใช้ได้ครบทั้งที่ไม่เคยเปิดเครื่องมือเหล่านั้นมาก่อน** (8/8 ผ่าน)

ข้อจำกัดที่ยังเหลือ: OCR ครั้งแรกต้องมีเน็ต เพราะชุดภาษาไทย (~10-30 MB) โหลดจาก CDN ของ Tesseract

## เครื่องมือทั้งหมด (16)

| กลุ่ม | เครื่องมือ |
|---|---|
| **เอกสารและจดหมายเวียน** | **จดหมายเวียน Word + Excel — เติมข้อมูลจาก Excel ลงเทมเพลต Word ทีละแถว** |
| จัดการ PDF | จัดการหน้า (ลบ/หมุน/สลับ) · รวมไฟล์ · แยกไฟล์ · บีบอัด · **ใส่ลายน้ำ** · OCR |
| แปลงจาก PDF | → รูปภาพ · → ข้อความ · → Word · → Excel |
| แปลงเป็น PDF | Word → · Excel → · รูปภาพ → |
| **PowerPoint** | **→ Word (ข้อความ+โน้ตผู้บรรยาย)** · **→ PDF (1 สไลด์ = 1 หน้า)** |
| รูปภาพ | แปลงชนิดไฟล์ · ย่อ–บีบอัด |
| ตารางและข้อมูล | Excel ⇄ CSV |

ทุกเครื่องมือรองรับภาษาไทยเต็มรูปแบบ (ตรวจแล้วด้วยการเปิดไฟล์ผลลัพธ์จริง ไม่ใช่แค่ดูว่าไม่ error)

## โครงสร้าง

```
FileKit/
├── index.html              หน้าเดียว + critical CSS ฝังใน (ไม่มี blocking script)
├── sw.js                   service worker (cache-first สำหรับ vendor)
├── manifest.webmanifest    ติดตั้งเป็นแอปบนเครื่องได้
├── src/
│   ├── app.js              เปลือกแอป: router + prefetch ตามเจตนา
│   ├── registry.js         ทะเบียนเครื่องมือ (ข้อมูลล้วน ไม่ import โค้ด)
│   ├── loader.js           ตัวโหลดไลบรารีแบบ on-demand + fallback CDN
│   ├── ui.js               ชิ้นส่วน UI ร่วม (dropzone, สถานะ, ปุ่ม, ช่วงหน้า)
│   ├── pdftext.js          อ่านโครงบรรทัด/คอลัมน์จาก PDF (ใช้ร่วม PDF→Word/Excel)
│   ├── thaifont.js         ฝังฟอนต์ไทยลง jsPDF
│   └── tools/*.js          1 ไฟล์ = 1 เครื่องมือ โหลดแยกกัน
├── vendor/                 ไลบรารี self-host + ฟอนต์ไทย subset
└── assets/                 CSS หน้าเครื่องมือ + ไอคอน PWA
```

## สิ่งที่เรียนรู้จากการใช้งานจริง (7 ก.ย. 2569)

ผู้ใช้เอาไฟล์ PowerPoint ใส่เครื่องมือ PDF→Word แล้วได้ข้อความว่า "ไฟล์นี้ไม่ใช่ PDF ที่ถูกต้อง หรือไฟล์เสียหาย"
ซึ่งทำให้เข้าใจผิดว่าไฟล์ตัวเองพัง ทั้งที่ไฟล์ปกติดี แค่มาผิดเครื่องมือ — จากเคสเดียวนี้แก้ไป 6 เรื่อง:

1. **ตรวจชนิดไฟล์ตั้งแต่ลากเข้ามา** (`src/filetype.js`) — บอกว่าไฟล์นี้คืออะไร และมีปุ่มพาไปเครื่องมือที่ถูกให้เลย
2. **เพิ่มเครื่องมือ PowerPoint 2 ตัว** — อ่าน .pptx เองด้วย JSZip + DOMParser (ไม่ต้องพึ่งเซิร์ฟเวอร์)
3. **ไฟล์ PDF ที่ล็อกรหัสผ่าน** — เดิมขึ้น `No password given` เป็นภาษาอังกฤษดิบและไปต่อไม่ได้
   ตอนนี้มีช่องใส่รหัสในหน้าเลย (`src/pdfopen.js` เป็นประตูเดียวที่ทุกเครื่องมือใช้)
4. **ไฟล์สแกน** — เดิมบอกให้ไปใช้เครื่องมือ OCR แยก ซึ่งคืนได้แค่ .txt = ทางตัน
   ตอนนี้ PDF→Word/Excel/ข้อความ เสนออ่านด้วย OCR ให้ในที่เดียว (`src/ocr.js`, โหลด Tesseract เมื่อกดปุ่มเท่านั้น)
5. **เลิกรายงานสำเร็จหลอก** — PDF→ข้อความ เคยนับตัวคั่นหน้าเป็นเนื้อหา ทำให้ไฟล์เปล่าถูกรายงานว่า "สำเร็จ 11 ตัวอักษร"
6. **โน้ตผู้บรรยายผูกผิดสไลด์** — เลขไฟล์ `notesSlide` ไม่ตรงกับเลขสไลด์ ต้องตามลิงก์ใน `_rels` เท่านั้น

## จดหมายเวียน (Mail Merge) — เรื่องที่ยากกว่าที่คิด

ฟีเจอร์นี้เอาข้อมูลจาก Excel เติมลงเทมเพลต Word ทีละแถว ได้เอกสารครบทั้งชุดในครั้งเดียว
งานลักษณะนี้มักมีข้อมูลอ่อนไหว (ชื่อ เงินเดือน เลขบัตรประชาชน) การทำในเบราว์เซอร์จึงได้เปรียบชัดเจน

**ใช้ `easy-template-x` (MIT) ที่ bundle เองไว้ใน `vendor/`** — เลือกตัวนี้เพราะ license สะอาดล้วน
ไม่มีฟีเจอร์ที่ต้องจ่ายเงินแม้แต่การแทรกรูป (ต่างจาก docxtemplater ที่ image/HTML/chart module เสียเงิน)
และพึ่ง JSZip เวอร์ชันเดียวกับที่โปรเจกต์นี้มีอยู่แล้ว

ไลบรารีเผยแพร่เป็น ESM ที่มี bare import ซึ่งเบราว์เซอร์แก้เองไม่ได้ จึง bundle ด้วย esbuild
พร้อมแทน `@xmldom/xmldom` ด้วย `DOMParser` ของเบราว์เซอร์ และแทน `jszip` ด้วยตัวที่โหลดไว้แล้ว
→ เหลือ **33 KB (gzip) จาก 85 KB**

**กับดักหลักคือ Word ไม่ได้เก็บข้อความเป็นก้อนเดียว** — ย่อหน้าหนึ่งถูกหั่นเป็นหลาย `<w:r>` (run)
ตามการจัดรูปแบบ การตรวจคำสะกด และประวัติการแก้ไข ตัวยึด `{{ชื่อ}}` ที่คนพิมพ์ติดกันบนหน้าจอ
จึงอาจกลายเป็น `{{ชื่` กับ `อ}}` คนละ run ในไฟล์จริง โค้ดที่ค้นหาทีละ run จะหาไม่เจอเลย

ตอนแรกเขียน engine เองและใช้งานได้จริง (ต่อข้อความทุก run เป็นสตริงเดียวก่อนค้นหา)
แต่ทำ **ตารางวนซ้ำ** ไม่ได้ ซึ่งเอกสารจริงเกือบทุกใบต้องใช้ — ใบเสนอราคา ใบเสร็จ ใบส่งของ
ล้วนมีรายการหลายบรรทัด จึงเปลี่ยนมาใช้ไลบรารีที่จัดการเรื่องนี้ครบแล้ว

**ทดสอบด้วยเคสที่หั่น run จริง:** สร้างไฟล์ทดสอบที่หั่นทุก 7 ตัวอักษรจนตัวยึด 7 จาก 8 ตัวถูกตัดกลาง
แล้วยืนยันว่ายังหาเจอครบและแทนที่ถูกต้อง โดยรูปแบบตัวอักษรเดิม (ตัวหนา) ยังอยู่

**สองโหมดการใช้งาน**
| โหมด | ใช้เมื่อไร | ตัวอย่าง |
|---|---|---|
| หนึ่งแถว = หนึ่งเอกสาร | ข้อมูลหนึ่งคนอยู่ในแถวเดียว | หนังสือรับรอง ป้ายชื่อ จดหมายเวียน |
| รวมหลายแถวเป็นเอกสารเดียว | เอกสารหนึ่งใบมีรายการหลายบรรทัด | ใบเสนอราคา ใบเสร็จ ใบส่งของ |

โหมดที่สองใช้กับเทมเพลตที่มีบล็อกวนซ้ำ `{{#รายการ}} … {{/รายการ}}` ในแถวตาราง
ระบบจัดกลุ่มแถวที่มีค่าตรงกัน (เช่นเลขที่ใบเสนอราคาเดียวกัน) ให้เป็นเอกสารเดียว
และ**เดาโหมดให้อัตโนมัติ**เมื่อพบว่าเทมเพลตมีบล็อกวนซ้ำและข้อมูลมีค่าซ้ำในคอลัมน์แรก

## ข้อจำกัดที่รู้อยู่

- **บีบอัด PDF** ใช้วิธีเรนเดอร์หน้าเป็นภาพ ได้ผลดีกับไฟล์สแกน (ทดสอบจริง 405 KB → 206 KB) แต่ข้อความจะกลายเป็นภาพ
  ระบบจะเตือนเมื่อบีบแล้วไม่เล็กลง (เช่นไฟล์ข้อความล้วน) แทนที่จะให้ไฟล์ที่แย่กว่าเดิม
- **PDF → Excel/Word** ใช้ได้กับ PDF ที่มีชั้นข้อความ ไฟล์สแกนต้องผ่าน OCR ก่อน · ไม่คงเซลล์ผสานและรูปภาพ
- **OCR** ครั้งแรกต้องดาวน์โหลดชุดภาษา (ไทยราว 10–30 MB) จาก CDN ของ Tesseract
- **PowerPoint → PDF** จัดหน้าขึ้นใหม่จากข้อความ ไม่ได้คัดลอกดีไซน์เดิม (สี รูป กราฟ ตำแหน่งจะไม่เหมือนต้นฉบับ)
  การคงหน้าตาเป๊ะต้องใช้ PowerPoint สั่ง Save as PDF เอง — เอนจินที่ทำได้จริงคือ LibreOffice ซึ่งรันในเบราว์เซอร์ไม่ไหว
- **PowerPoint → Word** ได้ข้อความ หัวข้อย่อย และโน้ตผู้บรรยาย แต่ไม่ได้รูปภาพในสไลด์
- ไฟล์ `.doc` / `.ppt` รุ่นเก่ายังไม่รองรับ (ต้องบันทึกเป็น .docx / .pptx ก่อน)
- **จดหมายเวียน** ยังไม่ได้เปิดใช้การแทรกรูปภาพจากข้อมูล (ไลบรารีรองรับแล้ว แต่ยังไม่ได้ทำ UI ให้)
  และการส่งออกยังเป็น .docx เท่านั้น ยังไม่ต่อท่อไปเป็น PDF ในคลิกเดียว
- ยังไม่มี: ใส่/ถอดรหัสผ่าน PDF, เซ็นเอกสาร, redact — ต้องใช้ไลบรารีตัวอื่น (qpdf-wasm / mupdf) เพิ่ม
